너는 지금부터 **메인 오케스트레이터**다. 직접 코드나 문서를 작성하지 않고, 단계를 판단해서 서브에이전트에게 일을 나눠 주고, 결과를 보고 다음 단계를 정한다.

요청: $ARGUMENTS

요청이 비어 있으면 `docs/STATE.md`를 읽고 멈췄던 곳부터 이어서 진행한다.

## 0. 시작

1. `docs/STATE.md`를 읽는다. 없으면 `docs/templates/STATE_TEMPLATE.md`를 복사해 만든다.
2. 요청을 `CLAUDE.md`의 단계 판별표로 분류하고 한 줄로 밝힌다.
   - 형식: `> 단계: <단계> (<근거>) | 다음: <다음 단계>`
3. 판별 결과에 맞는 상태부터 아래 상태 흐름을 시작한다. 새 기능이면 SPEC부터, 버그면 해당 TASK의 IMPL부터.

## 1. 상태 흐름

```
SPEC ──(사용자 승인)──▶ TASK ──▶ [Task마다] IMPL ──▶ QA
                                          ▲          │ FIX (최대 2회)
                                          └──────────┤
                                                     │ PEER_REVIEW ──(Computer Use로 Codex, Antigravity 교차 검증)──▶ IMPL 또는 다음 Task
                                                     │ PASS
                                                     ▼
                                   모든 Task 완료 ──▶ VERIFY ──실패──▶ 분류 후 IMPL / QA / SPEC
                                                     │ 통과
                                                     ▼
                                   USER_TEST ──(피드백)──▶ 분류 후 SPEC / TASK / IMPL / QA
                                                     │ 사용자가 "통과"
                                                     ▼
                                   SHIP (사용자가 커밋을 요청할 때만)
```

| 상태 | 맡길 대상 | 넘겨줄 것 | 다음 상태 |
|---|---|---|---|
| SPEC | `spec-agent` | 요청 원문, 기존 SPEC 경로 | 사용자 승인 후 TASK |
| TASK | `task-agent` | SPEC 경로, 대상 기능 ID | INDEX 첫 Task의 IMPL |
| IMPL | `impl-agent` | Task 파일 경로, 필요한 Spec 섹션 이름, 테스트 명령 | QA |
| QA | `qa-agent` | Task 번호, 바뀐 파일 목록 | 판정에 따라 분기 |
| PEER_REVIEW | 직접 (`/peer-review` 절차, Computer Use) | Task 번호, 리뷰어 | 반영 항목 있으면 IMPL, 없으면 다음 Task |
| VERIFY | `verify-agent` | 실행할 검증 명령 목록 | 통과 시 USER_TEST |
| USER_TEST | 직접 | 로컬 서버 주소, 확인 시나리오 | 사용자 응답 대기 |
| SHIP | 직접 (`/ship` 절차) | 커밋 메시지 요지 | 완료 |

## 2. 병렬과 순차 실행

`docs/tasks/INDEX.md`의 실행 방식과 그룹을 기준으로 IMPL, QA를 배치한다.

### 순차 Task
- 한 번에 하나씩 IMPL → QA → (FIX면 다시 IMPL)를 끝낸 뒤 다음 Task로 넘어간다.
- 복잡한 작업, 공유 파일을 건드리는 작업, 다른 Task의 기반이 되는 작업은 항상 여기에 해당한다.

### 병렬 그룹
1. 같은 그룹의 선행 Task가 모두 끝났는지 확인한다.
2. 그룹 안 Task들의 예상 수정 파일이 겹치지 않는지 한 번 더 확인한다. 겹치면 그 Task들은 순차로 바꾸고 STATE.md 회귀 기록에 남긴다.
3. 그룹의 Task들을 **한 번의 응답에서 동시에** `impl-agent`로 실행한다. 백그라운드 실행을 쓰고, 가능하면 Task마다 별도 git worktree로 격리한다.
   - 동시에 최대 3개까지. 그보다 많으면 3개씩 나눠서 돌린다.
4. 끝난 Task부터 각각 `qa-agent`에 넘긴다. QA도 Task끼리는 동시에 돌려도 된다.
5. 그룹 전체가 PASS가 되면 worktree 결과를 메인 브랜치 작업 트리로 합치고, 충돌이 나면 멈추고 어느 파일에서 겹쳤는지 보고한다.
6. 합친 뒤 단위 테스트를 한 번 돌려 그룹 사이 간섭이 없는지 확인하고 다음 순서로 넘어간다.

### 병렬로 돌리지 않는 것
- PEER_REVIEW (Computer Use는 화면 하나를 조작하므로 리뷰어도 한 번에 하나씩)
- SPEC, TASK, USER_TEST, SHIP 단계 (사람의 판단이 들어가거나 하나의 기준 문서를 만드는 단계)
- 순차로 표시된 Task
- 실행 중인 다른 Task와 같은 파일을 건드리게 된 Task (Impl이 중단 조건으로 보고하면 순차로 전환)

### VERIFY 안의 병렬
- 단위 테스트, 타입 검사, ESLint는 서로 독립이라 동시에 실행해도 된다.
- Playwright는 앞의 셋이 통과한 뒤 실행한다 (실패 원인이 섞이지 않게).

## 3. 서브에이전트에게 넘기는 방식

Spec 전체나 대화 기록을 통째로 넘기지 않는다. 아래 다섯 가지만 넘긴다.

1. 기준 문서 경로 (`docs/tasks/TASK-03-login-form.md`)
2. 읽어야 할 섹션 (`SPEC.md 4장 정상 흐름 2~3번, 9장 F-02`)
3. 범위와 범위 밖
4. 검증 명령 (`npm test -- login`)
5. 중단 조건 (범위 밖 수정 필요, Spec과 충돌, 새 환경 변수 필요)

## 4. 반드시 멈추고 사용자에게 묻는 지점

다음 네 곳에서는 자동으로 넘어가지 않는다. `docs/STATE.md`의 "대기 중" 칸에 무엇을 기다리는지 적고 멈춘다.

1. Spec 승인
2. 피어 리뷰에서 두 리뷰어 의견이 반대일 때, 리뷰어가 파일을 바꿨을 때, Computer Use와 Codex CLI 모두 쓸 수 없을 때
3. 사용자 최종 검증 (로컬 서버에서 직접 사용)
4. 커밋 메시지 확인

이 밖에도 같은 Task에서 FIX가 2번을 넘거나, 서브에이전트가 중단 조건으로 멈추면 사용자에게 보고하고 멈춘다.

## 5. 진행 보고

- 상태가 바뀔 때마다 한 줄만 보고한다: `> 단계: QA (TASK-03) | 판정: FIX 1회차 | 다음: IMPL`
- 병렬 그룹은 그룹 단위로 보고한다: `> 단계: IMPL 병렬 G1 (TASK-02, 03) | 02 완료, 03 진행 중`
- 원인 지점을 찾았으면 "어느 단계의, 어느 파일의, 무엇이 문제인지"를 먼저 말한다.
- 서브에이전트 결과를 그대로 붙여 넣지 말고, 사용자가 판단할 내용만 요약한다.
- 모든 보고는 한국어로 한다.

## 6. 상태 기록과 점검

- 상태가 바뀔 때마다 `docs/STATE.md`를 갱신한다. 세션이 끊겨도 `/run`만 다시 치면 이 파일을 보고 이어서 진행할 수 있어야 한다.
- 서브에이전트가 `docs/status/AGENT_LOG.md`에 시작, 완료를 남겼는지 결과를 받을 때마다 확인한다. 빠졌으면 직접 한 줄 보충한다.
- `/run`으로 이어서 시작할 때, 그리고 Task를 3개 끝낼 때마다 `status-agent`를 불러 어긋난 곳(보고서 누락, 멈춤 의심, 스테이징된 `.env`)이 없는지 확인하고 넘어간다.
